# Implementation plan: check for a stale canonical workspace before acting

## Executive summary

`tt` is a bash CLI that manages a tree of tasks on top of the `jj` version control system. Every
mutating `tt` command runs inside a *transaction*: the VCS operation ID is recorded before the
command starts, and if the command fails, the transaction is rolled back by restoring the repository
to that operation.

That rollback is performed in the **canonical** repository — the original repo directory, as opposed
to the additional `jj` workspaces (called *worktrees* in tt's vocabulary) that tasks are checked out
into. In `jj`, a workspace becomes **stale** when a rewrite performed elsewhere changes the commit
that workspace's on-disk files belong to; `jj` then refuses every command in that workspace that
needs its working copy — the rollback's `op restore` included. In a repository driven from task
worktrees, the canonical workspace is rarely the one being worked in, so it can sit stale
indefinitely, and a rollback that needs it fails. When that happened, the failure was reported as a
warning, the in-progress history entry was deleted anyway, and the repository was left
mid-transaction with no lock and no trace of the problem.

This task makes three changes:

1. **Refuse up front.** Before any write, a command checks that the workspace it depends on is not
   stale, and refuses with a clear message naming that workspace and how to recover it.
2. **Keep the lock on a failed rollback.** When the restore inside a rollback fails, the in-progress
   history entry is kept, so the next `tt` command refuses instead of running against a half-written
   repository, and the failure is reported as an error carrying the recovery instructions.
3. **Add `tt worktree refresh`.** A new command that recovers a stale workspace — the command every
   new refusal points at.

## 1. Background

### Vocabulary

| Term | Meaning |
|---|---|
| **canonical repository** | The original repo directory. Its `.jj/repo` is a *directory* (the operation store). |
| **worktree** | An additional `jj` workspace attached to the same repository. Its `.jj/repo` is a *file* containing a relative path back to the canonical repo's `.jj/repo`. tt checks tasks out into these. |
| **invoking worktree** | The workspace the user ran the `tt` command from. |
| **working-copy commit (`@`)** | The commit a workspace's files currently belong to. Every workspace has its own. |
| **bare operation** | A VCS operation run with `--ignore-working-copy`: it rewrites the commit graph and touches no workspace's files. tt uses these for almost all writes. |
| **behind** | A worktree whose branch has advanced past it. Its files are valid, just old. Fixed with `tt worktree sync`. |
| **stale** | A workspace whose recorded working-copy commit was rewritten by a bare operation, so its files no longer match any current commit. `jj` refuses all working-copy commands there. Fixed with `jj workspace update-stale` — which is what the new `tt worktree refresh` drives. |

**Behind and stale are different conditions.** A bookmark advancing past a worktree leaves it
*behind*; a bare rewrite of its `@` leaves it *stale*. This was verified empirically (see §2).

### The failure being fixed

```
Rolling back transaction (restoring VCS operation: 83a967b8fddd...)
Error: The working copy is stale (not updated since operation 83a967b8fddd).
Warning: Could not restore the VCS operation state; manual recovery may be needed
```

The rollback ran `jj op restore` in the canonical repository, whose workspace was stale. The restore
was refused. The rollback nonetheless deleted the in-progress history entry, so the next `tt` command
ran happily against a repository left mid-rebase with a task bookmark on a conflicted commit.
Recovery required running `jj op restore` by hand from a workspace that was not stale.

### Empirical findings (verified against jj 0.43 during research)

| Probe | Result |
|---|---|
| An operation performed in another workspace, unrelated to this one | workspace stays healthy |
| A bookmark advancing past a workspace (workspace *behind*) | stays healthy — *behind* ≠ *stale* |
| A bare rewrite that changes the tree of a workspace's `@` | workspace becomes **stale** |
| `jj op restore` run from a stale workspace | refused — the bug this task addresses |
| `jj op restore --ignore-working-copy` run from a stale workspace | succeeds |
| `jj op restore` run from a healthy workspace while another is stale | succeeds |
| `jj debug working-copy` in a stale workspace | succeeds; records **no** operation |
| `jj debug working-copy` in a healthy workspace holding uncommitted edits | records **no** operation |
| `jj debug local-working-copy` in a healthy workspace holding uncommitted edits | **records an operation** (snapshots) |
| `jj workspace update-stale` in a healthy workspace holding uncommitted edits | **records an operation** (snapshots) |
| `jj workspace update-stale` against a stale workspace holding uncommitted edits | **on-disk edits destroyed** (`removed 3 files`; see jj issue #7229) |
| `jj workspace list -T <template>` | exposes no staleness keyword (`WorkspaceRef` has only `name`, `target`, `root`) |
| `jj -R <path> ...` from an unrelated working directory | correctly selects `<path>`'s workspace, for both `@` resolution and `debug working-copy` |
| `jj op abandon` of a workspace's recorded operation | produces a *third* state: jj reports an internal error about a sibling operation, distinct from stale |

Consequences that shape the implementation:

- There is **no** user-facing backend command that reports staleness without snapshotting the
  working copy, so detection must be built from `jj debug working-copy` plus bare reads.
- Recovering a stale workspace **destroys** uncommitted work there. Recovery is therefore an
  explicit, `--force`-gated command, never automatic.
- Workspace states exist that are neither healthy nor stale, so detection must have a third
  "could not determine" outcome and must fail loudly rather than guess.

### Which commands touch a foreign worktree's working copy

Audited across the whole CLI. Only these four load a workspace other than the invoking one; every
other command reaches the repository through bare operations and is unaffected by staleness:

| Command | Foreign access | Resolved before the transaction opens? |
|---|---|---|
| `tt worktree sync <path>` / `--all` | snapshots and rebases the target | yes |
| `tt task checkout --worktree[=path]` | checks the target clean; starts/commits its working copy | yes (`scripts/cli/task/checkout` lines 245-265, transaction at 282) |
| `tt task checkin --delete` | checks the child worktree clean, or snapshots it before deleting | yes (`scripts/cli/task/checkin` lines 277-283, transaction at 357) |
| `tt worktree switch` | checks the outgoing worktree is clean | n/a — switch opens no transaction |

### Commands that write to a branch

These 14 already call `_worktree__ensure_working_copy "$repo" || exit 1` and are where the canonical
guard is added: `task create`, `task edit`, `task checkout`, `task checkin`, `task complete`,
`task delete`, `task move`, `task rename`, `task reorder`, `task propagate`, `task publish`,
`task checkpoint`, `task context add`, `task context delete`.

### Coding rules

`.agents/rules/bash-style.mdc` and `.agents/rules/markdown-style.mdc` are mandatory. In particular:
`#!/usr/bin/env bash` plus `set -euo pipefail` in every command; a `usage()` function printing to
stdout on `--help` (exit 0) and to stderr on bad arguments (exit 1); all arguments parsed before any
action; diagnostics to stderr, output to stdout; errors propagated. Documentation must describe only
the current state — no version history, no "previously…" notes, and no verbatim source code.

## 3. Decision log

| # | Decision | Rationale |
|---|---|---|
| 1 | Refuse up front rather than reworking where the rollback restores from | The rollback's use of the canonical repo is deliberate: it is the one workspace guaranteed to exist after the invoking worktree has been deleted. A precondition that refuses before any write is strictly more useful than a warning issued while the command is already failing. |
| 2 | A residual gap is accepted, not closed | A command that *itself* rewrites the canonical workspace's `@` makes it stale mid-run; its rollback still cannot restore. Made survivable by decisions 3 and 9 rather than by moving the restore. |
| 3 | A failed restore keeps the in-progress history entry | The kept entry is a lock: the next `tt` command refuses with the existing "Another tt command is in progress" error instead of running against a half-written repository. |
| 4 | Detection must be strictly read-only | A check that runs before every branch-writing command must not record an operation. Ruled out every user-facing probe, all of which snapshot. |
| 5 | The backend primitive prints the commit the files match | `_jj__get_worktree_checkout_revision`; the staleness comparison then lives in the worktree model rather than the backend. |
| 6 | Three-state detection; never guess | `_worktree__check_stale` returns 0 stale / 1 healthy / 2 undetermined. Undetermined is a hard failure with tt framing; the backend's own text reaches the user through `TT_LOG`. |
| 7 | One path-taking guard plus a canonical wrapper | `_worktree__ensure_worktree_current REPO WORKTREE` and `_worktree__ensure_canonical_current REPO`. |
| 8 | The canonical guard skips nested calls and the invoking worktree | Both skips are load-bearing, not optimizations — see §5. |
| 9 | A failed rollback reports an error naming the operation ID and both exits | `tt history undo --force` to retry the revert, `tt history unlock --force` once recovered by hand. |
| 10 | `tt worktree refresh` is a new command, not a flag on `sync` | "Move a worktree forward" and "recover a workspace whose files no longer match any commit" are different operations; only the second can destroy uncommitted work. |
| 11 | `refresh` takes a single target; no `--all` | `--all` would sit badly with `--force` semantics: one flag authorizing destruction across an unbounded set. |
| 12 | `refresh` opens no transaction | A transactional refresh of a stale canonical workspace could not roll itself back, and refresh must stay usable while a stale lock is present. |
| 13 | `refresh --force` bypasses detection entirely | Guarantees a route out of any state tt cannot classify, including the operation-divergence state. |
| 14 | `refresh` prints one line | Backend detail is available through `TT_LOG=info`, as for every other command. |
| 15 | `sync` screens all targets and refuses the whole run if any is stale | With `refresh` available the user can restore consistency themselves; that is better than partially self-healing and committing a still-inconsistent repository. |
| 16 | `sync` keeps a defensive runtime check, worded identically | Covers a worktree that goes stale between the screening and its turn. |
| 17 | The four foreign-worktree commands guard their target up front | Replaces a raw backend error surfacing mid-command. |
| 18 | User-facing term is "stale" | It is the word in every backend error the user will have just read, and tt already uses "stale" for a transaction lock. |
| 19 | Messages state condition and action only | No speculation about cause; consequences stated plainly ("uncommitted changes in that workspace will be lost"). |
| 20 | One shared harness helper creates the stale state | `make_worktree_stale`; the mechanism is defined once rather than in seven suites. |


**Fallout policy.** The canonical guard only activates when a command is invoked from a worktree
other than the canonical repository, which in the suite means the 50 `run_tt_in_worktree` call sites
across 12 suites. If one of those tests now fails:

1. If the test's own setup left the canonical workspace stale — fix the test.
2. If a `tt` command left it stale — **stop and report it**; that is a genuine finding about tt, not
   a test defect.
3. If the guard fired when the workspace was not stale — fix the guard.

The guard's semantics are not weakened to make a test pass without raising it first.

### Step 1 — Detect a stale workspace

**Files:** `scripts/cli/lib/vcs/jj.sh`, `scripts/cli/lib/vcs/jj.test.sh`, `scripts/cli/lib/repo.sh`,
`scripts/cli/lib/worktree.sh`, `scripts/cli/lib/worktree.test.sh`, `scripts/harness/harness.sh`,
`ARCHITECTURE.md`.

**1a. Backend primitive.** Add to the "Working copy (restricted)" group of `lib/vcs/jj.sh`:

```
# Usage: _jj__get_worktree_checkout_revision WORKTREE
_jj__get_worktree_checkout_revision() {
  # 1. read the workspace's recorded state:   __jj__read WORKTREE debug working-copy
  # 2. extract the operation ID from the "Current operation: OperationId(\"...\")" line
  # 3. fail (return non-zero, print nothing) when no ID could be extracted
  # 4. print the workspace's @ commit AS OF that operation:
  #      __jj__read WORKTREE --at-operation <op> --ignore-working-copy \
  #        log -r '@' --no-graph -T 'commit_id'
}
```

Its header comment must state: what it prints (the commit ID the workspace's on-disk files were last
updated to, which may differ from the commit the repository now records for that workspace); that it
is a pure read that records no operation and updates no files; that it works against a stale
workspace; and *why* the low-level state query is used — every user-facing alternative
(`jj debug local-working-copy`, `jj workspace update-stale`, any ordinary working-copy command)
snapshots the working copy and records an operation, which a check running before every
branch-writing command must not do.

`-R WORKTREE` selects the target workspace regardless of the caller's working directory, for both
the state query and the `@` resolution, so no `cd` wrapper is needed.

**1b. Backend contract.** Add the 1:1 wrapper to `lib/repo.sh`, in the working-copy group:

```
_repo__get_worktree_checkout_revision() { _jj__get_worktree_checkout_revision "$@"; }
```

**1c. Detection.** Add to `lib/worktree.sh` (and to its header's public surface list):

```
# Usage: _worktree__check_stale REPO WORKTREE
#   0 — WORKTREE is stale
#   1 — WORKTREE is not stale
#   2 — WORKTREE's state could not be determined
_worktree__check_stale() {
  matched="$(_repo__get_worktree_checkout_revision WORKTREE)" || return 2
  [[ -n "$matched" ]] || return 2
  current="$(_repo__resolve_commit WORKTREE '@')" || return 2
  [[ -n "$current" ]] || return 2
  [[ "$matched" != "$current" ]]
}
```

Status 2 is never folded into either boolean: tt does not guess at a state it could not read.
`REPO` is accepted for signature consistency with the rest of the module even though the comparison
needs only `WORKTREE`.

**1d. Harness helper.** Add to `scripts/harness/harness.sh`, beside the other state helpers:

```
# Usage: make_worktree_stale WORKTREE
# Leaves WORKTREE's on-disk files behind the commit they belong to, the way a
# bare rewrite performed from another workspace does.
make_worktree_stale() {
  # 1. ensure WORKTREE's @ has file content that a rewrite can change
  #    (write a file and let the workspace snapshot it)
  # 2. bare-rewrite that commit's tree from OUTSIDE the workspace:
  #      jj -R <repo> --ignore-working-copy restore --from 'root()' --into '<name>@'
  #    addressing the workspace by name so the rewrite cannot be attributed to it
  # 3. assert the backend now refuses a working-copy command there, so a jj
  #    behaviour change fails loudly here rather than silently disarming
  #    every test that depends on the state
}
```

**1e. Tests.**

`lib/vcs/jj.test.sh` — beside the existing `_jj__refresh_worktree` tests:

- `test__jj__get_worktree_checkout_revision__matches_wc_commit_when_healthy`
- `test__jj__get_worktree_checkout_revision__reports_the_pre_rewrite_commit_when_stale`

### Step 2 — `tt worktree refresh`

**Files:** `scripts/cli/worktree/refresh` (new, executable), `scripts/cli/worktree/refresh.test.sh`
(new), `scripts/cli/tt`, `DESIGN.md`, `.agents/skills/tt/SKILL.md`.

**2a. The command.** Model its shape on `scripts/cli/history/unlock` (silent no-op when there is
nothing to do; refusal without `--force`) and its argument handling on `scripts/cli/worktree/sync`.

```
tt worktree refresh [<path>] [--root] [--force] [--repo PATH]
```

```
main:
  parse all arguments first (bash-style rule):
    <path>        at most one positional
    --root        target the canonical workspace
    --force       perform the recovery
    --repo PATH   repository root override
    -h|--help     usage to stdout, exit 0
    anything else usage to stderr, exit 1
  if <path> and --root were both given: usage to stderr, exit 1

  # Detect the current worktree from the CWD BEFORE resolving the repository,
  # exactly as sync does: --repo or TT_REPO would otherwise name a repository
  # root that has nothing to do with where the user is standing.
  if no <path> and no --root:
    target = _worktree__find_current  (error + exit 1 when the CWD is in no worktree)

  repo = _workspace__resolve_repo "$repo_flag"
  if --root: target = _workspace__resolve_canonical_repo "$repo"
  if <path>: target = _path__resolve_symlinks "$path", verified with
             _worktree__resolve_name (error + exit 1 when it is not a worktree
             of this repository, same wording as sync's)

  if --force:
    _repo__refresh_worktree "$target" || { error; exit 1 }
    log "Refreshed $target"
    exit 0

  _worktree__check_stale "$repo" "$target"; case $? in
    1) exit 0 ;;                                   # healthy: no output at all
    0) log the stale refusal (see message catalogue); exit 1 ;;
    2) log the undetermined refusal;                exit 1 ;;
  esac
```

Constraints:

- **No transaction.** `_history__begin_transaction` is never called. Refresh is a recovery
  operation, like `tt workspace init`: a transactional refresh of a stale canonical workspace could
  not roll itself back, and refresh must stay usable while a stale lock is present. State this in
  the command's header comment.
- **`--force` bypasses detection entirely**, so there is a route out of states tt cannot classify.
- **One line of output.** The backend's own account of what changed on disk is available through
  `TT_LOG=info`.
- There is no `--all`.

**2b. Alias.** In `scripts/cli/tt`, add `refresh) set -- worktree refresh "${@:2}" ;;` to the alias
table in `main()` and `tt refresh → tt worktree refresh` to the alias list in `usage()`.

**2c. Tests** (`scripts/cli/worktree/refresh.test.sh`, new suite):

- `test_worktree_refresh__healthy_worktree_is_a_silent_no_op` — exit 0, no output, repository
  unchanged
- `test_worktree_refresh__stale_worktree_refuses_without_force` — exit 1, message names the
  workspace, mentions `--force`, and states uncommitted changes will be lost; the workspace is still
  stale afterwards
- `test_worktree_refresh__force_recovers_a_stale_worktree` — exit 0, `Refreshed <path>`, and a
  working-copy command in that workspace succeeds afterwards
- `test_worktree_refresh__root_targets_the_canonical_workspace` — run from a task worktree with the
  canonical workspace stale
- `test_worktree_refresh__path_targets_that_worktree`
- `test_worktree_refresh__defaults_to_the_current_worktree`
- `test_worktree_refresh__path_with_root_is_rejected` — exit 1, usage on stderr
- `test_worktree_refresh__unknown_path_is_rejected`
- `test_worktree_refresh__records_no_transaction` — `assert_history_count` unchanged across a
  `--force` run
- `test_worktree_refresh__alias_dispatches` — `tt refresh --help` reaches the command

**2d. Documentation.** DESIGN.md gets §6.16, the command reference entry, and the alias table row;

### Step 3 — Staleness guards

**Files:** `scripts/cli/lib/worktree.sh`, `scripts/cli/lib/worktree.test.sh`, `ARCHITECTURE.md`.

Add beside `_worktree__ensure_working_copy`, and to the module header's public surface list:

```
# Usage: _worktree__ensure_worktree_current REPO WORKTREE
_worktree__ensure_worktree_current() {
  case _worktree__check_stale REPO WORKTREE in
    1) return 0
    0) log the stale refusal naming WORKTREE and the refresh command ; return 1
    2) log the undetermined refusal naming WORKTREE                  ; return 1
}

# Usage: _worktree__ensure_canonical_current REPO
_worktree__ensure_canonical_current() {
  [[ -z "${TT_TRANSACTION_ID:-}" ]] || return 0        # nested call
  canonical="$(_workspace__resolve_canonical_repo REPO)" || return 1
  worktree="$(_repo__resolve_worktree_root REPO)"       || return 1
  [[ "$canonical" -ef "$worktree" ]] && return 0        # same workspace
  _worktree__ensure_worktree_current REPO "$canonical"
}
```

`-ef` compares the two paths as filesystem entries, which is required: the canonical resolver may
return its argument unchanged while the worktree resolver canonicalizes symlinks, so a string
comparison would report two names for the same directory as different.

Document both skips as load-bearing, in the function header:

- **Nested calls.** A parent command's own writes can make the canonical workspace stale. A nested
  guard would then refuse mid-transaction, and the rollback that refusal triggers is precisely the
  one staleness breaks — turning a survivable situation into a locked repository. The check belongs
  once, before anything is written.
- **Canonical is the invoking worktree.** The invoking worktree is left to fail on its own terms:
  the transaction's begin-time snapshot refuses immediately and rolls back cleanly. The guard
  therefore runs only where it is load-bearing — a canonical workspace nobody is standing in.

`_worktree__ensure_worktree_current` has neither skip: it is asked about a worktree the command is
about to touch, including when that is the invoking one.

### Step 6 — Keep the lock on a failed rollback

**Files:** `scripts/cli/lib/history.sh`, `scripts/cli/lib/history.test.sh`, `DESIGN.md`,

```
  if ! _repo__restore_operation "$canonical_repo" "$before_op"; then
    rm -rf "$preserve_dir"                 # discard, do not re-apply
    log the multi-line error (see message catalogue)
    trap - ERR EXIT
    unset _TT_TRANSACTION_OWNER
    unset TT_TRANSACTION_ID

```

- The preserved copies are discarded unre-applied: a failed restore never disturbed the files, and

  the history *entry* survives, which is what makes the damage visible to the next command.
