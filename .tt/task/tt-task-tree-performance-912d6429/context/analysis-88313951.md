# Implementation Plan: fix `--focus` merged-map coverage

## Root cause

`build_merged_map` is keyed by *task ID* and scans every branch per ID. Focus mode only feeds it the ancestor chain, so children rendered at the leaf fall back to their own (post-checkin, stale) bookmarks. The fix inverts the loop: index every branch's `subtask:` entries **once**, then derive both maps from that index.

## Current vs. proposed call graph

```
BEFORE                                   AFTER
main                                     main
 ├ focus:                                 ├ build_subtask_index   (1 read per branch)
 │   chain walk  O(levels × branches)     ├ parent_map_from_index (no I/O)
 │   build_merged_map(chain only) ← BUG   ├ merged_map_from_index (no I/O)
 │   emit_tree                            ├ focus:
 └ full:                                  │   chain walk via parent_map (no I/O)
     collect_task_ids(merged_map="")      │   emit_tree
     build_merged_map(all ids)            └ full:
     emit_tree                                collect_task_ids(merged_map)
                                              emit_tree
```

## Change 1 — extract the repeated suffix idiom

The `task/*` / `project/*` stripping is duplicated in five places in `tree`, and it hardcodes prefixes rather than using the configured `task_prefix` / `project_prefix`. Add one helper:

```bash
# Usage: branch_suffix BRANCH TASK_PREFIX PROJECT_PREFIX
# Outputs the slug-hex part of a task or project branch name.
# Returns 1 if BRANCH is neither a task nor a project branch.
branch_suffix() {
  local branch="$1" task_prefix="$2" project_prefix="$3"
  if is_task_branch "$branch" "$task_prefix"; then
    printf '%s' "${branch#"$task_prefix"}"
  elif is_project_branch "$branch" "$project_prefix"; then
    printf '%s' "${branch#"$project_prefix"}"
  else
    return 1
  fi
}
```

Callers become `suffix="$(branch_suffix "$branch" "$task_prefix" "$project_prefix")" || continue`. Note this requires threading `task_prefix`/`project_prefix` into `build_merged_map`'s replacement and `collect_task_ids`, which currently don't receive them.

## Change 2 — `build_subtask_index` replaces `build_merged_box`

```bash
# Usage: build_subtask_index REPO BRANCHES TASK_PREFIX PROJECT_PREFIX
# Reads each branch's own task file exactly once and emits one line per
# subtask: entry found, in branch order:
#   CHILD_ID<TAB>CHECKBOX<TAB>OWNER_BRANCH
build_subtask_index() {
  local repo="$1" branches="$2" task_prefix="$3" project_prefix="$4"
  local branch suffix path content
  for branch in $branches; do
    [[ -z "$branch" ]] && continue
    suffix="$(branch_suffix "$branch" "$task_prefix" "$project_prefix")" || continue
    path="$(task_file_path "$suffix")"
    content="$(jj_show_at_revision "$repo" "$branch" "$path")" || continue
    [[ -z "$content" ]] && continue
    while IFS='|' read -r cb id _title; do
      [[ -z "$id" ]] && continue
      printf '%s\t%s\t%s\n' "$id" "$cb" "$branch"
    done < <(get_subtask_entries "$content")
  done
}
```

Two derived views, both pure text processing (no `jj`):

```bash
# Checked-in tasks only: the branch they were merged into is authoritative.
# Output format is unchanged from the old build_merged_map: "TASK_ID:BRANCH".
merged_map_from_index() {
  printf '%s\n' "$1" | awk -F'\t' '$2 == "[x]" && !seen[$1]++ { print $1 ":" $3 }'
}

# Any checkbox state: child -> owning parent branch, for the focus chain walk.
parent_map_from_index() {
  printf '%s\n' "$1" | awk -F'\t' '!seen[$1]++ { print $1 "\t" $3 }'
}
```

`!seen[$1]++` preserves the existing first-branch-wins semantics (the old code `break`s on first match in the same branch order), so `emit_tree` needs no change to consume `merged_map`.

## Change 3 — build the index once in `main`

Replaces both existing `build_merged_map` call sites, hoisted above the focus/full split:

```bash
  local subtask_index merged_map parent_map
  subtask_index="$(build_subtask_index "$repo" "$all_task_project_branches" \
    "$task_prefix" "$project_prefix")"
  merged_map="$(merged_map_from_index "$subtask_index")"
  parent_map="$(parent_map_from_index "$subtask_index")"
```

This is what actually fixes the bug: focus mode now hands `emit_tree` a map covering **every** task, not just the chain.

Bonus fix at tree:466 — `collect_task_ids` is currently called with an empty merged_map (`""`), so the full listing's reachable-set traversal also reads from stale bookmarks and can silently drop the descendants of any checked-in task. It can now receive the real map:

```bash
reachable_ids="$(collect_task_ids "$repo" "$projects_to_show" "$all_task_project_branches" "$merged_map")"
```

## Change 4 — chain walk uses `parent_map`

Replaces tree:396-416 (the inner `for branch in ...` scan and its `jj` call per level):

```bash
    local chain="$current_bookmark"
    local current="$current_bookmark"
    while true; do
      local parent
      parent="$(printf '%s' "$parent_map" | awk -F'\t' -v id="$current" \
        '$1 == id { print $2; exit }')"
      [[ -z "$parent" ]] && break
      # Guard against a cycle in malformed subtask metadata.
      if printf '%s' "$chain" | grep -qFx "$parent"; then
        log "Warning: Cycle detected in task hierarchy at '$parent'; stopping ancestor walk."
        break
      fi
      chain="${parent}"$'\n'"${chain}"
      current="$parent"
    done
```

The cycle guard is new — the current loop would spin forever on a metadata cycle.

## Change 5 — parent-entry fallback for unreadable task files

`emit_tree` already parses the parent's checkbox and title but discards them:

```bash
while IFS='|' read -r sub_cb sub_id sub_title; do   # sub_cb, sub_title unused
```

Thread them into the recursive call as two new trailing parameters and into `get_metadata_from_content`, applying them **only when the task file could not be read at all**:

```bash
get_metadata_from_content() {
  local content="$1" fallback_checkbox="${2:-}" fallback_title="${3:-}"

  # No readable task file: fall back to the parent's subtask: entry, which
  # records the checked-in state even when the task's own file is missing.
  if [[ -z "$content" ]]; then
    printf '%s|%s' "${fallback_checkbox:-[ ]}" "${fallback_title:-(no title)}"
    return 0
  fi
  ... existing parse ...
}
```

A file that *is* readable but lacks a `status:` line keeps its current `TODO` default, so no existing behavior shifts.

Note that in practice, `subtask:` parent entries store only the ID, without a title:

```
subtask: [ ] task/tt-workspace-doctor-fe9143d1
```

So in practice this fallback recovers the **checkbox** (`[x]` instead of `[ ]`) but the title still renders `(no title)`. The `sub_title` plumbing is there because `get_subtask_entries` supports it and it costs nothing.

Note `get_metadata_from_content`'s current signature takes `task_id`, `merged_branch`, `all_branches`, `repo` — **none of which are used in the body** - these should be dropped while changing the signature.

## Change 6 — tests

New scenarios in `scripts/cli/task/tree.test.sh`, using existing harness helpers (`create_project`, `create_task`, `checkout_task`, `checkin_task`):

```bash
test_task_tree__focus_shows_checked_in_sibling_title() {
  setup_workspace "tree-focus-checkedin"
  proj_id=$(create_project "proj" "Project") || true
  checkout_task "$proj_id" >/dev/null || true
  done_child=$(create_task "done" "Done Child") || true
  checkout_task "$done_child" >/dev/null || true
  checkin_task --complete >/dev/null || true      # advances proj, not done_child
  checkout_task "$proj_id" >/dev/null || true

  output="" exit_code=0
  output=$(run_tt task tree --focus 2>&1) || exit_code=$?
  assert_success "focus succeeds" "$exit_code"
  assert_contains "checked-in child title" "$output" "Done Child"
  assert_not_contains "no missing title" "$output" "(no title)"
}

test_task_tree__focus_matches_full_listing_for_checked_in_children() {
  # Same setup; assert the child's rendered line is identical in both modes.
}
```

Run with `scripts/test task/tree`, plus `scripts/test task/checkin task/show task/parent` since `collect_task_ids` behavior shifts.
