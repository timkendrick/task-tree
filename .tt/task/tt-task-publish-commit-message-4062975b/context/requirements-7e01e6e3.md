# Requirements: Prompt for `tt task publish` commit message

Task: `task/tt-task-publish-commit-message-4062975b`

## 1. Summary

`tt task publish` currently derives the free-text portion of both commit messages it
creates from the `title:` frontmatter field of the project's task file. It must
instead obtain that text from the user, either interactively (editor prompt, as
`tt task checkpoint` does) or non-interactively via a new `-m/--message` flag.

Optionally, the message may carry an auto-generated **change summary** produced by
`tt task changelog`, describing everything on the project branch since it last
diverged from the target branch.

## 2. Command surface

```
tt task publish [<project-id>] --target <branch>
                [-m|--message <msg>]
                [--changelog [--changelog-depth <n>]]
                [--rebase | --merge] [--force]
                [--repo PATH] [--workspace-dir PATH]
```

New options:

| Option | Meaning |
| --- | --- |
| `-m`, `--message <msg>` | Commit message text; skips the editor prompt. |
| `--changelog` | Append a change-summary section to the message. |
| `--changelog-depth <n>` | Subtask depth passed through to `tt task changelog --depth`. Only valid together with `--changelog`. |

### 2.1 Argument validation

- `--changelog-depth` **without** `--changelog` is a usage error: print usage to
  stderr and exit non-zero. (The depth would otherwise have no observable effect.)
- `--changelog-depth` takes the same value domain as `tt task changelog --depth`
  (non-negative integer; `0` = checkpoints only). Invalid values are a usage error.
- Omitting `--changelog-depth` while passing `--changelog` means "every level",
  i.e. `tt task changelog` is invoked without `--depth`.
- `-m` and `--changelog` are **compatible** (see §4.2).
- All existing options and their validation are unchanged.

## 3. Message acquisition

### 3.1 Interactive (no `-m`)

An editor is opened, seeded with the template in §4. The resulting buffer is
cleaned as follows:

1. Lines whose first character is `#` are removed.
2. Trailing whitespace on each line is removed.
3. Leading and trailing blank lines are removed.
4. **Leading whitespace within a line is preserved** — the nested indentation of
   `tt task changelog`'s task tree must survive the round trip verbatim.

This differs from the existing shared `prompt` helper, which strips leading
whitespace from every line and would therefore flatten the changelog tree.

If the editor exits non-zero, publish aborts non-zero (existing `prompt_raw`
behaviour: the temp file is retained and its path reported).

### 3.2 Empty message

If the cleaned message is empty, publish prints an error and exits non-zero. No
commits are created and no bookmark moves.

This is reachable even with `--changelog`: the user may delete the pre-populated
change-summary section along with everything else.

### 3.3 Non-interactive (`-m <msg>`)

The supplied text is used as-is (no `#`-stripping, no editor). An empty `-m ''`
is an empty message and therefore an error per §3.2.

## 4. Change summary section

### 4.1 Content

Generated by:

```
tt task changelog --task <project-id> --since <target> [--depth <changelog-depth>] --repo <repo>
```

The section appended to the message is, byte for byte:

```
<LF>
Change summary:<LF>
<LF>
<changelog output, ending in exactly one LF>
```

i.e. one blank separator line, the literal header `Change summary:`, one blank
separator line, then the verbatim `tt task changelog` output.

When `tt task changelog` produces no output, the placeholder line `No code changes`
is used in place of the changelog output.

Literal strings: header is `Change summary:` (trailing colon); placeholder is
`No code changes` (no trailing period).

#### Example — non-empty changelog

```

Change summary:

- `task/a-1111aaaa` - Parent task
  - `task/b-2222bbbb` - Child task
- `c0ffee12` - some checkpoint message
```

#### Example — empty changelog

```

Change summary:

No code changes
```

### 4.2 Placement

- Interactive: appended to the (empty) message template before the editor opens,
  so the user can read, edit, or delete it. Whatever survives editing becomes part
  of the commit message.
- With `-m <msg>`: appended directly to `<msg>`; no editor opens.
- Without `--changelog`: nothing is appended; the interactive template's message
  area is empty.

### 4.3 Timing

The changelog is generated — and the editor opened — **after** any
`--rebase`/`--merge` propagation from the target has completed and after the
post-propagation clean-working-copy check, so that the summary reflects exactly
the history about to be published. Both happen **before** the publish transaction
is opened, so an aborted/empty message leaves no VCS state to unwind.

### 4.4 Never-published projects

When the project branch has never been published to the target, the reference
commit is the most recent common ancestor of the project branch and the target.

Verified against jj 0.43: even for entirely disjoint histories, `fork_point(a | b)`
resolves to the virtual root commit `0000…0`, and
`first_ancestors(tip) ~ ::<root>` yields the branch's full history. The existing
`tt task changelog --since <target>` behaviour therefore already reports the whole
project history in this case, and **no special handling is required**. This must be
covered by a test.

### 4.5 Changelog failure

`tt task changelog` cannot realistically fail here — publish has already validated
that both the project bookmark and `--target` resolve, and §4.4 shows the fork
point always exists. Defensively, a non-zero exit from `tt task changelog` aborts
publish with an error before the editor opens and before any commits are created.

## 5. Commit messages

The hardcoded prefixes are unaffected:

- The **publish** merge commit is described as
  `[tt:task:<project-id>:publish] <user message>`, where `<user message>` is the
  cleaned message from §3, including any surviving change-summary section. It may
  be multi-line.
- The **handoff** commit is unchanged: `[tt:task:<project-id>:handoff] <project-title>`,
  still sourced from the task file's `title:` frontmatter field.

## 6. Interactive template

Template layout (hint lines last; all `#` lines are stripped before use):

```
<empty message area>

Change summary:

<changelog output or "No code changes">

# Project: <project-id>
# Target: <target>
# An empty message cancels the publish.
```

Without `--changelog`, the change-summary block is omitted, leaving an empty
message area followed by the hint lines.

## 7. Testing

- Update every existing case in `scripts/cli/task/publish.test.sh` to pass
  `-m "<msg>"` so no case blocks on an editor.
- New cases:
  - `-m` message lands in the `[…:publish]` commit; handoff commit still carries
    the project title.
  - Editor path (stub `TT_EDITOR`): message from the editor lands in the publish
    commit.
  - Empty editor message → non-zero exit, target bookmark unmoved, no new commits.
  - `-m ''` → non-zero exit.
  - `--changelog` with checked-in subtasks: publish commit contains
    `Change summary:` followed by the changelog lines, with nesting indentation
    preserved.
  - `--changelog` with nothing to report: `No code changes` placeholder.
  - `--changelog` on a never-published project: summary covers the project's full
    history (§4.4).
  - `--changelog-depth` limits the reported depth.
  - `--changelog-depth` without `--changelog` → usage error, non-zero exit.
  - Editor buffer with the changelog section deleted → empty-message abort.
